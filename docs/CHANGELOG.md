# Changelog

Changes that are merged but not yet in a release go under **Unreleased**. Newest first.

## Unreleased

- Roles and permissions (#6). The role of an account (`admin` or `user`) is now checked on every API call, and the UI shows a user only **Runs**.
  - **After the upgrade:** accounts with the role `user` can only use Runs, their own repository list and their own credentials. No command changes a role yet; create an admin with `scf user create --admin` under another e-mail if you need one.
  - **What users may do.** List and read their own runs, start a saved flow, follow, cancel, resume, approve and reject (with a note) their own runs, list the published flows (name and description only), and manage their repositories and credentials. Everything else answers `403 {"error":"not allowed for your role"}`. A run that is not theirs, unknown, without an owner or with an unreadable `run.json` answers `403 {"error":"not your run"}`. Starting a run: `yaml` gives 403 "only an admin can run a flow that is not saved", `repo` gives 403 "only an admin can choose the folder", a bad flow name gives 400, an unknown flow 404, and a `github_repo` that is not one of the user's repositories gives 403 `"<name>" is not one of your repositories` (or `set the var "github_repo" to one of your repositories`). A flow without `github_repo` runs in the server's default folder, with the variables it had when it was queued.
  - **A user account is for people you trust with the machine.** A run executes commands as the server's Mac user, with the server's GitHub access. Roles limit the API and the pages, not what a run can do. To switch user runs off, change the rule `POST runs` to `no` in `src/server/permissions.ts`.
  - **404 for calls without a rule.** The table in `src/server/permissions.ts` decides first. A call with no rule now answers `404 {"error":"not found"}` for every role, also paths with extra segments (`/api/info/x`) and `POST /api/flows`, `GET /api/blocks/x` and `PUT /api/credentials`, which answered 405 before.
  - **`owner`** (the account id) is saved in `run.json` and `queue.json`, and is in the run briefs. Runs of watchers, the CLI and older versions have none and are admin-only. Old files load unchanged. The scheduler never gives the same run id twice, and a bad `run.json` no longer breaks the admin runs list.
  - **Repositories.** New `repos.json` in the data folder (mode `0600`) and `GET /api/repos`, `POST /api/repos {name}` (201, 409, 400; at most 50) and `DELETE /api/repos/<owner>/<name>`. `scf user delete` also removes the list, and stops before anything else changes when `repos.json` cannot be read.
  - **New files.** `src/auth/repos.ts`, `src/server/permissions.ts`, `src/server/api-repos.ts`, `tests/permissions.test.ts`, `tests/repos.test.ts`. The guide has a new part "Roles and permissions" with the generated table.
  - **Not included.** Runs that use a user's stored credentials, changing your own password in the UI, pages for users (starting runs, repositories), an admin view of other accounts' repositories, and isolation of user runs. The repository list is not a security boundary.

- First line in comments (#51): every Foundry comment that asks you something or reports a failure now starts with one bold line, `**What you need to do:** …` — questions up front, the planner's questions, a risky plan, a split, the push approval and the failure comment. A plan that starts coding by itself starts with `**Nothing needed from you** — it is being worked on.` The line comes from the next-step record (`firstLine()` in `src/next-step.ts`). Steps get it as `FACTORY_FIRST_QUESTIONS`, `FACTORY_FIRST_PLANNER_QUESTIONS`, `FACTORY_FIRST_APPROVE_PLAN`, `FACTORY_FIRST_APPROVE_SPLIT`, `FACTORY_FIRST_APPROVAL` and `FACTORY_FIRST_NOTHING` (also as `SCF_FIRST_…`). The failure comment no longer has a separate "What you can do" bullet; the first line says it. Headings, closing sentences and hidden markers are unchanged; `failureComment()` now takes the record. Runs started earlier keep their old text when resumed.
- Access from other computers (#20). New `server` settings (Settings → Network, or `config.yaml`): `listen` (default `127.0.0.1`; one of `127.0.0.1`, `::1`, `0.0.0.0`, `::`; needs a restart), `allowed_hosts` (replaces the fixed localhost check; live) and `allow_insecure_http` (default off; live). The user guide has a new section "Access from other computers" with a Caddy setup, what any proxy must do, and troubleshooting.
  - **HTTPS rule.** A request from another computer is refused with `403 HTTPS required` unless it comes over HTTPS through a proxy on this Mac (loopback peer with `X-Forwarded-Proto: https`), or `allow_insecure_http` is on. Forwarded headers are trusted only from a loopback peer. Unlisted hosts still get `403 forbidden host`.
  - **Origin check is stricter.** A change needs the exact origin of the request: scheme, name and port. Before, the scheme was ignored and `localhost` and `127.0.0.1` counted as the same.
  - **Headers.** Over HTTPS the session cookie is `Secure` and responses have `Strict-Transport-Security: max-age=31536000`. Every response has a strict `Content-Security-Policy` and `X-Content-Type-Options: nosniff`. The plain-HTTP cookie is unchanged. The import map is gone: `ui/app.js` and `ui/library.js` import `/vendor/yaml/index.js`.
  - **Safety.** The server does not start on `0.0.0.0` or `::` without an admin account (it exits with a message naming `scf user create --admin`). `POST /api/setup` works only from the Mac itself. `PUT /api/config` answers 400 when the change would lock out the sending browser. `GET /api/info` has `listening`. A malformed URL such as `/%` now gets 400 instead of an error.
  - **Sign-in limits.** Besides the limit per e-mail: 60 tries per client address in 15 minutes (the address comes from `X-Forwarded-For` only for a proxy on this Mac), at most 16 password checks at once (else 429), and an e-mail longer than 254 characters is a wrong sign-in.
  - New `src/server/net.ts` holds the access rules. Not included: built-in TLS, a proxy on another machine, listening on one LAN address, a public URL for Slack links. After the first save `config.yaml` has a `server:` block, which an older build would reject.
- Stored credentials (#13). A user can store a token or an ssh key; it is encrypted, never shown again, and hidden from logs and output. There is no UI page yet, and runs do not use stored credentials yet. **macOS only:** the key lives in the macOS Keychain.
  - **Storage.** `credentials.json` in the data folder (mode `0600`, copied unchanged by the data-folder move). Each secret is encrypted with AES-256-GCM. The 32-byte master key is in the macOS Keychain (service `claude-factory-credential-key`, one item per key id), never in the data folder. The id, owner, type, name, created time and fingerprint are bound to each ciphertext, so changing any of them makes decryption fail. Writing the key is read back to check it.
  - **API.** `GET /api/credentials` (your own), `POST /api/credentials {type, name, secret}` (201) and `DELETE /api/credentials/<id>`. An answer holds only `id`, `type`, `name`, `created`, `lastUsed` and `fingerprint` (the first 16 hex digits of the SHA-256 of the secret). Types are `token` (8 to 4096 printable ASCII characters, one line, trimmed) and `ssh-key` (a PEM private key, up to 16384 characters, stored with LF line ends). 400 for bad input, 409 for a name you already use, 404 for an unknown id. If the store fails the answer is a plain 500 and the server log names the file and kind, never a value.
  - **Redaction.** Stored secrets (also JSON-escaped and URL-encoded, and the lines of a multi-line key) become `[redacted]` in step output, step logs, transcripts, the live log, run errors and reasons, scheduler and server log lines, the CLI's top-level error, and every authenticated API answer (`send()`), including text saved before the secret was stored. Output of a process is filtered line by line through one filter for the combined log, so halves on stdout and stderr cannot join. A partly printed line is held until its newline. Redaction follows `credentials.json` while a process runs. If credentials exist and the Keychain cannot be read, runs fail before they start ("the stored credentials cannot be read") and the API and logs show nothing from the changed store (fail closed).
  - **Wiping.** Deleting a credential or a user (`scf user delete`) replaces the master key (or drops it when no credential is left), so an older copy of the file cannot be read. An old key that cannot be removed from the Keychain is kept in `retiredKeyIds` and retried on every write; `DELETE` then answers 500, the CLI exits 1, and repeating the call or running `scf credential rotate-key` cleans it up.
  - **CLI.** `scf user delete <e-mail>` (account, sessions and credentials; refuses the only admin), `scf credential rotate-key` (re-encrypts everything under a new key) and `scf credential check` (stores, reads and removes a probe item).
  - **Code.** New `src/credentials/{keychain,store,redact,cli}.ts` and `src/server/api-credentials.ts`; `runProcess` takes an optional `redactor`; `withAuthLock` users call `removeCredentialsLocked`. `SCF_SECURITY_BIN` replaces `/usr/bin/security` and is for tests (the fake is `tests/fixtures/fake-security.mjs`).
  - **Not covered.** A UI page, using credentials in runs, other platforms, text written before a credential was saved (it is hidden in API answers but stays on disk), the task text in `run.json`, and other encodings such as base64 of `user:token`. Anyone who runs commands as your macOS user, flow steps included, can read the key.
  - **Please check once.** The real `/usr/bin/security` was not run when this was written: run `scf credential check` and `scf credential rotate-key` from a Terminal window.

- A health line at the top of every page (#56). Under the top bar every page says "All good", or the number of problems of the Foundry itself and one sentence for each, with its action and a link. It refreshes on every page change and every 30 seconds, and says so when the server does not answer. The problems are:
  - a server that waits to restart ("A new version is waiting — it restarts after 2 runs");
  - a usage limit, one per agent (Claude, Codex), for runs that stopped in the last hour, with the time it continues; a used-up daily budget (the link goes to Settings);
  - a watcher error, which names the repository, and a watcher that has not checked for 3× its interval (not while the server waits to restart);
  - an issue closed on GitHub while its run still works, with a **Cancel run** button that asks for confirmation;
  - runs that failed because of the Foundry (newest per issue, not replaced, finished in the last 7 days, at most 5). The line names the failure and its fix without the reason; the run page has the reason.
  - The time of the last successful check is shown per repository.
  - New `GET /api/health` (`ok`, `summary`, `problems`, `repos`), built in `src/server/health.ts` with `src/next-step.ts`. It holds only record fields: no titles, settings, tokens or paths, and links are only `https://…` or `#/…`. `GET /api/next` is unchanged.
  - The **Server** card on the Dashboard is gone; the health line replaces it.
  - A watcher error now names its repository everywhere ("The watcher for acme/app has an error"). A connection problem (`cannot access … with gh`, no host, `dial tcp`, timeout, HTTP 5xx) reads "The watcher for acme/app can't reach GitHub" with the action "Check the network and `gh auth status`". **Error details** now also show gh's first output line (`errorLine()` in `src/errors.ts`).

- Sign-in (#47): everyone signs in to the web UI with their own account. **After the upgrade, open the UI once and create the admin account on the setup page (or run `scf user create --admin`).** Until an admin exists the UI shows only that page, and `scf serve` / `scf ui` print a hint. There is no setting that turns sign-in off. The CLI, the watchers and runs that are already going need no account.
  - **Sign-in page and sign-out.** The UI shows a sign-in form, or "Create the admin account" while there is no admin. The signed-in name and a **Sign out** button are in the top bar. A call that gets 401 (the session ended) reloads the page, which then shows the form.
  - **API.** `GET /api/session` (`{ user | null, csrfToken?, setupNeeded }`), `POST /api/session {email, password}` (sign in), `DELETE /api/session` (sign out) and `POST /api/setup {name, email, password}` (the first admin; 409 once an admin exists) are public, like the static files. Every other `/api/…` route answers 401 `sign in first` without a session, also when the data folder has moved (the 503 for a moved folder, which names the new folder, is only shown to signed-in users). Sign-in answers 401 `wrong e-mail or password` for a wrong password and for an unknown e-mail alike, 403 for a blocked account (only after the password was right) and 429 after 10 wrong tries for one e-mail in 15 minutes (kept in memory; a restart clears it). Passwords are used exactly as typed, spaces included.
  - **Cookie.** `scf_session_<port>` with `HttpOnly; SameSite=Strict; Path=/; Max-Age=604800`. The port is in the name because cookies on `localhost` are shared between ports. There is no `Secure` flag, because the server speaks plain HTTP on 127.0.0.1. A new sign-in always makes a new token and ends the session of the cookie it came with.
  - **Sessions.** Kept in `sessions.json` in the data folder (mode `0600`, only the SHA-256 of the token). They last 7 days, are not renewed, survive a restart and move with the data folder. A missing, corrupt or invalid file counts as no sessions.
  - **CSRF.** Every call that is not a GET or HEAD needs the header `X-CSRF-Token` with the token from `GET /api/session` or from sign-in, else 403. Sign-in and setup are covered by the Origin check and the JSON content type.
  - **Sessions end** after sign-out, expiry, a password change or a block. `scf user password` and `scf user block` remove that account's sessions too. A sign-in that was checked against the old password cannot create a session after the change. An open run log stream is closed within 5 seconds (`ServerOptions.sessionRecheckMs`, default 4000, is for tests).
  - **Errors.** If the account files cannot be read or written, or are locked, sign-in answers a plain 500 `sign-in is not working; see the server log`. The server log has the file name and the kind of problem, never a path, password or hash.
  - **Roles are stored, not enforced.** Every active account can use every route until permissions are added.
  - New: `src/auth/sessions.ts`, `src/server/api-auth.ts`, `ui/auth.js`; `adminHint()` in `src/auth/cli.ts`; `checkSignIn()` and `startSession()` in `src/auth/users.ts`. Out of scope: managing accounts and changing a password in the UI, permissions per role, access from other machines, TLS.

A **?** next to each status shows the record's two sentences; it opens with a click, Enter/Space or a tap. `GET /api/watchers` has a new `state` on each watcher (`name`: `active`, `error` or `disabled`, plus `status` and `help`), so the watcher's own state has a **?** too; an error is called "watcher error". - A run that failed because of the Foundry says so and suggests the fix (#55). New module `src/failure.ts` (`classifyFailure`) sorts why a run did not finish into four causes: code, factory (the Foundry or its environment), limit and decision. Factory is chosen only on known messages: a blocked agent command, a push blocked by the protected-branch guard, a marker the Foundry could not read (no `PLAN_STATUS` line, no questions to ask, no `SUBTASK` lines), an internal error, an unknown step, a run that failed before any step ran (workspace, bot identity, GitHub App token) and an interrupted run. Failing tests, guards, reviews, too many visits and the secret scan stay code; budgets and the usage limit are limit; questions and approvals are decision. When in doubt it is code.
  - For a factory failure the next-step record reads "The Foundry failed, not the code: …", its action is the suggested fix followed by how to retry, and who is "Something is wrong". The same sentence shows on the run page, the Runs list, the watcher card, the Dashboard and in notifications. The `failed` help text has a factory version. Code failures keep their wording. Records of failed or interrupted runs carry the new field `cause` (`code`, `factory`, `limit` or `decision`) in `GET /api/runs`, `/api/queue`, `/api/watchers` and `/api/next`. An interrupted run gets `cause: "factory"` but keeps its own record, because a watched one resumes by itself. Runs saved before this change get a record too.
  - Step records have a new optional `denied`: the tool calls Claude Code refused (at most 5, `git push` left out), read from `permission_denials`. The live log shows each as `⚠ blocked: …`. The sentence shows only the tool and program of a blocked command (e.g. `Bash: curl`). When a command was blocked in a step before a code failure, the sentence gets a short hint. Absent for Codex, older Claude Code and older runs.
  - The failure comment on the issue starts with "itself failed on this issue, not the code" for a factory failure and ends with the record's sentence, so the fix is in it. The hidden marker is unchanged. No new label: the issue keeps the failed label and `status_labels` settings keep working.

It has five groups: stories done, stories merged into develop, releases to main, failed runs and things newly waiting for you (the same items as Your turn, without dismissed ones).

A run that failed shows under failed, unless a newer run of the same issue replaced it or it was interrupted. A *release* is a merged pull request whose body has the `release` or `daily` Foundry marker; ordinary Foundry pull requests do not count. Eval runs are left out. Flows without steps named `commit` or `push_develop` never show under done or merged.
  - **Per browser.** The last visit is kept in this browser (`localStorage`, key `scf.since`) and shared by its tabs. **Dismiss** hides the strip in all tabs and moves the visit forward. Nothing shows when nothing changed.
  - New API: `GET /api/since?since=<time>` (400 when the time is missing or invalid; a future time counts as now). The answer has `groups`, `total`, `complete` and `notes`. Nothing is stored on the server. Releases are read from GitHub for the repositories of all watchers (also disabled ones) and of the newest runs, at most 20, with an 8 s time limit, and a good answer is reused for 15 s.

  - `gh()` and `ghJson()` in `src/github.ts` take an optional time limit (`timeoutMs`); existing callers are unchanged. The modified time of `run.json` is now rounded to the millisecond instead of cut off (it could read 1 ms too low).
- Notifications only when it is your turn (#40): macOS and Slack now tell you only when something lands in Your turn (question, risky plan or split, release pull request, failure, watcher error), grouped ("3 things need you") and at most once per 5 minutes. A click opens the item.

It never lists running, queued, limit-paused or waiting-for-another-story work, nor evaluation runs. Each item shows what, why (from the next-step record), one primary link and since when. - Words (#48): one glossary (`src/words.ts`) decides the Foundry's words. Every next-step record has two new fields: `status`, a short plain status name such as "waiting for you — questions" or "paused — usage limit", and `help`, two sentences on what it means and what happens next. `GET /api/runs`, `/api/queue`, `/api/watchers` and `/api/next` return them. A pull request that brings finished work to main is now always called "release pull request" (the watcher's line said "daily pull request"). Label descriptions on GitHub say what the label means and what to do; the trigger label and, when the watcher sets `vars.review_plan_label`, the review label get one too. Existing labels get the new text the next time the server starts. The user guide has a new section "Words the Foundry uses".
- Watchers keep labels true and show their last successful check (#54): every check now compares the status label with the run. A run that is running or queued (e.g. approved or resumed in the UI) gets the working label, and the right label when it ends. A label that does not match the newest run is corrected (e.g. failed but the run waits for approval). A done label is left alone, and an issue without a status label starts over as before. An issue closed on GitHub while its run is running, queued or waiting for approval is not changed: the watcher reports one record (`closed_elsewhere`, "cancel the run if the work is no longer wanted") on its card, the Dashboard Waiting card, the run page, `GET /api/next` and the queue — unless the run closed the issue itself (report, split, merge). Cancel now also works on a run that waits for approval (the run becomes `cancelled`; removing a queued approval from the queue cancels it too), and a run cancelled on a closed issue only loses its status labels, with no failure comment. `WatcherStatus` has `lastOk` and `startedAt`; the Watchers page shows "last successful check …" instead of "last check". A watcher that has not finished a check for more than 3× its interval shows the new `watcher_stale` record (not together with an error, and not while the server waits to restart). A failed closed-issue scan and a wrong interval now show as a watcher error, and a check that takes longer than 10 minutes is given up so "Check now" works again. Activity lines name the label they set.
- Accounts (#46): new `scf user create|list|password|block|unblock`. Accounts are stored in `users.json` in the data folder (mode `0600`; a new data folder gets `0700`). Passwords are hashed with scrypt (N=32768, r=8, p=3, 64-byte key, 16-byte random salt per user). The password is asked twice on a terminal, or read from the first line of stdin — never an option or an environment variable. A file that cannot be read or is not valid is an error, never "no accounts". Two processes that change the store at once do not undo each other. Nothing needs an account yet.
