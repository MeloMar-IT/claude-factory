- Self-repair 2 — more monitor detectors (#86).
  - **New detectors** (each has a threshold under `monitor:` in `config.yaml`): **stuck run** (nothing written to the log for longer than the step's timeout plus 10 minutes; a step without a timeout counts 120 minutes), **same step keeps failing** (the same step of a flow ended runs as failed for 3 different issues in 24 hours), **label and run disagree** (more than 3 checks), **lock without owner** (a code-area lock or a run lock held by a run that is not running, more than 10 minutes), **queue not moving** (jobs queued, slots free, nothing started for 15 minutes), **restart overdue** (a new version waits more than 2 hours), **develop is red** (the tests after a merge into develop failed 2 times in a row, looking back 24 hours) and **slow step** (more than 3 times the usual time, 3 times in 24 hours).
  - **Normal is never a finding.** A run that waits for a person, a usage limit that resets by itself, a sign-out, a story that waits for a dependency or a release, and a `done` label are left out. Interrupted runs, rejected approvals and the run budget do not count as a failing step. A run inside a sub-flow step is not judged as stuck.
  - **Descriptions.** Every detector has a two-sentence `description`; `detectorInfo()` lists them (and `detector-failed`) for the app.
  - **The monitor keeps running while a new version waits** (`WatcherManager.drain()`), so a restart that takes too long is seen. `stopAll()` still stops it.
  - **Formats.** New `monitor:` keys (`stuck_run`, `same_step_failing`, `label_mismatch`, `orphan_lock`, `queue_stalled`, `restart_overdue`, `develop_red`, `slow_step`) that an older build rejects once the config is saved. The findings file and `GET /api/queue` are unchanged.
  - **Code.** New `src/monitor/work-detectors.ts`; `slowVisits()` in `src/estimate.ts`; `labelLies()` and `TrackedIssue.labelOff` in `src/queue/watcher.ts`; `Scheduler.lastStart()`; `lastLogWrite()`, `readAreaLocks()` and `areaLockDir()` in `src/monitor/monitor.ts`; `pidAlive` is exported from `src/engine/state.ts`.
  - **Not included.** Showing findings or descriptions in the app.

- The monitor (#85): a watcher that finds problems of the Foundry itself. Add a watcher with `source: monitor` (admin only; `id`, `every`, `enabled`; no repository, flow, label or owner; only one per install; not there until added). Each check runs five detectors with thresholds in the new `monitor:` section of `config.yaml`: restart loop (more than 5 resumes in 10 minutes; `resumes` at most 49), watcher error (more than 3 failed checks in a row, grouped by kind), GitHub request limit (hit, or more than 80% used; read from `gh api rate_limit` at most once a minute), watcher silent (no check for 5 intervals), unexplained failure (no rule explains it; minor). A detector that crashes becomes a finding. Findings (fingerprint, severity, summary, evidence, first/last seen, count) are stored in `monitor-findings.json` in the data folder; not seen for 24 hours means gone. The monitor only writes findings. Also: `run.json` gains `resumeLog` (the last 50 resumes), the status in `GET /api/watchers` gains `errorCount`, a failing monitor check shows in Health, and `scf watch --source monitor` is refused (it only runs in the server). Not included: a page or API for findings, reporting to GitHub, mutes.
- Hotfix path for bug stories (#89).
  - **Behaviour.** In `issue-gitflow`, an issue with a label in `hotfix_labels` (default `bug`, any case) is built as a hotfix: branch `hotfix/<issue>-<title>` from the `main` commit the tests passed on, the same plan, checks, build, tests, reviews and docs as a feature. After the reviews the fix is merged into `main` (no fast-forward), tested, and pushed only when green; if `main` moved, it merges and tests again; red tests or a conflict push nothing and fail with a clear message. Then `main` is merged into `develop` with the usual conflict handling and tests. The issue is closed when the fix is on `main`. The merged branch is deleted (`delete_merged_branches`), unless it got new commits after the merge. A hotfix is never split by itself; a risky plan still waits for a person. No pull request, tag or release note.
  - **Develop behind.** If `develop` cannot take the fix, the fix stays on `main` and the comment says so (first line `Merge main into develop…`) and what happens next. The comment on a finished hotfix says whether the running Foundry has the fix (only for the Foundry's own repository).
  - **Option.** New `hotfix_to_main` in `config.yaml` (default `false`; **Hotfixes** in Settings → Safety). **Changed for existing installs:** nothing, until an admin switches it on; a bug story is built as a feature, and its report has one line saying why. An older build rejects the new key. New flow variables `hotfix_labels` and `hotfix_prefix`.
  - **Protection of `main`.** The one exception to **Protected branches**: only `push_main` of the unchanged built-in `issue-gitflow` may push `main`, with a one-time token the engine writes for that step; setting `FACTORY_PUSH_ALLOW` by hand gives nothing. It is not a hard wall (a command that skips git hooks still gets through): use GitHub branch protection for that. If GitHub only accepts pull requests on `main`, the run fails and says so.
  - **Formats.** New first lines `_FIXED` and `_MERGE_BACK`; new step variables `$FACTORY_HOTFIX`, `$FACTORY_SELF_SHA`, `$FACTORY_SELF_REPO`.
  - **Code.** `scripts/build-flows.mjs` (steps `baseline_main` … `hotfix_done`, `report`), `hotfixState`, `pushAllowEnv`, `grantPush` and `selfBuild` in `src/engine/guards.ts`, `src/engine/execute.ts`, `runClosedIssue` in `src/next-step.ts`, `ui/admin.js`.

- Failures explained (#39).
  - **Behaviour.** A failed run explains itself in plain words: what failed, why, the kind of problem, what the Foundry already tried ("3 fix attempts", tries inside a step, resumes) and four options (Retry, Retry with a hint, Change the plan, Close). It is shown as a card at the top of the run page and in the failure comment on the issue. The four kinds: a problem in the code, a problem with the environment or the Foundry, a limit, a person's decision. When the fix needs a new run (for example a used-up run budget), Retry says "start a new run" instead of "resume".
  - **Model call.** After a failed run whose rules say "code", one short call to a small model (`failure_summary.model`, default `haiku`) reads the end of the failing output and writes one sentence. The call has no tools (`--tools ""`), no MCP servers and no GitHub tokens, runs in an empty temp folder with a 45 second limit, and costs at most 0.05 USD or what is left of the run and daily budgets (no call below 0.01 USD). It does not run for stopped or cancelled runs, for limits, decisions and Foundry failures, or for Codex models. The cost is added to the run. The answer is redacted and cleaned (no Markdown, links, mentions or folders) and kept as `failureNote`; the page and the comment say when a model wrote the sentence. A model answer of "environment" turns a code failure into a Foundry failure. The terminal state is saved first, the note in a second save. Resuming removes the note. The log of the call is `logs/failure-summary.log`.
  - **Option.** `failure_summary.enabled` (default `true`) and `failure_summary.model` in `config.yaml`. Switch the call off for tests and special setups with `SCF_NO_FAILURE_MODEL=1` / `FACTORY_NO_FAILURE_MODEL=1`. Codex-only installs get the rules text; a local model works with `model: ollama:<model>`.
  - **Formats.** New optional `failureNote` (`kind`, `why`, `by`) in `run.json`; optional `retried` (`blips`, `models`) and `unreachable` on a step record; new `failure_summary` key in `config.yaml`. Old files load unchanged. An older build rejects a `config.yaml` that has the new key.
  - **Changed.**
    - On a failed run page the summary card replaces the "What happens next" block, the page opens on Steps (unless you picked a tab), and the raw reason moved into the collapsed **Raw details** of the card. "Show the failed step" opens that step.
    - The failure comment has What happened, Why, Kind of problem, Already tried and Your options, also when the Foundry itself failed.
    - A step budget failure counts as a limit, a rejection as a person's decision, and repeated rejections that use up `max_visits` stay a decision. At `max_visits` the summary names the step that failed last.
    - Git or gh login and network errors, wrong model or provider settings and a missing `claude` or `codex` program count as a Foundry failure.
    - A limit, an unreachable service or a `max_budget_usd` stop inside a parallel or sub-flow step is read from the failing child step.
    - A signed-out agent reads "paused — signed out" and an unreachable AI service (also an overloaded one, HTTP 529) "paused — AI service not reachable"; both read "paused — usage limit" before. A real quota or rate limit (429) still reads "paused — usage limit".
    - The comment's "Last failing step" and its raw details come from the step that explains the failure, not from a parallel or sub-flow wrapper.
  - **Code.** New `src/failure-explain.ts` (`explainFailure`, `explainPrompt`, `parseNote`, `noteFrom`); `src/failure.ts` gets `failureSummary`, `triedOf`, `triedText`, `safeSentence`, `hideFolders`; `runClaude` gets the `noTools` option and a stable "claude CLI not found" error; `isQuotaError` in `src/agents/targets.ts`; `failure` on the next-step record (`NextStep.failure`); `failureCard` and `failedStepIndex` in `ui/runs.js`.
  - **Not included.** Buttons for Change the plan and Close (both work through GitHub today and are described in words); a failure card for paused runs; a field for `failure_summary` on the Settings page.
  - **Needs a check with the real CLI.** It assumes the installed `claude` accepts `--tools ""`. If not, the call fails and the rules text is used.

- One status comment per issue (#53).
  - **Behaviour.** An issue watcher keeps one comment on every issue it follows with the next step (the record the app shows, in plain words for a reader of the issue). It is edited, never posted again. It also covers done issues, a wait for the scheduled release, an issue closed while its run works, and an issue the watcher no longer follows (last text). Two watchers on one issue share the comment. Status comments never count as questions, answers or approval requests. Extra status comments of the Foundry's own account are removed (at most 5 per read); a comment of another account is never touched.

  - **First check after the upgrade.** One new comment (one notification) per open issue a watcher tracks, at most 30 per check; the rest follows at the next check. A check spends at most 60 seconds on comments, and a failing comment only shows in the log.

- Stored credentials (#13). A user can store a token or an ssh key; it is encrypted, never shown again, and hidden from logs and output. There is no UI page yet, and runs do not use stored credentials yet. **macOS only:** the key lives in the macOS Keychain.
  - **Storage.** `credentials.json` in the data folder (mode `0600`, copied unchanged by the data-folder move). Each secret is encrypted with AES-256-GCM. The 32-byte master key is in the macOS Keychain (service `claude-factory-credential-key`, one item per key id), never in the data folder. The id, owner, type, name, created time and fingerprint are bound to each ciphertext, so changing any of them makes decryption fail. Writing the key is read back to check it.
  - **API.** `GET /api/credentials` (your own), `POST /api/credentials {type, name, secret}` (201) and `DELETE /api/credentials/<id>`. An answer holds only `id`, `type`, `name`, `created`, `lastUsed` and `fingerprint` (the first 16 hex digits of the SHA-256 of the secret). Types are `token` (8 to 4096 printable ASCII characters, one line, trimmed) and `ssh-key` (a PEM private key, up to 16384 characters, stored with LF line ends). 400 for bad input, 409 for a name you already use, 404 for an unknown id. If the store fails the answer is a plain 500 and the server log names the file and kind, never a value.
  - **Redaction.** Stored secrets (also JSON-escaped and URL-encoded, and the lines of a multi-line key) become `[redacted]` in step output, step logs, transcripts, the live log, run errors and reasons, scheduler and server log lines, the CLI's top-level error, and every authenticated API answer (`send()`), including text saved before the secret was stored. Output of a process is filtered line by line through one filter for the combined log, so halves on stdout and stderr cannot join. A partly printed line is held until its newline. Redaction follows `credentials.json` while a process runs. If credentials exist and the Keychain cannot be read, runs fail before they start ("the stored credentials cannot be read") and the API and logs show nothing from the changed store (fail closed).
  - **Wiping.** Deleting a credential or a user (`scf user delete`) replaces the master key (or drops it when no credential is left), so an older copy of the file cannot be read. An old key that cannot be removed from the Keychain is kept in `retiredKeyIds` and retried on every write; `DELETE` then answers 500, the CLI exits 1, and repeating the call or running `scf credential rotate-key` cleans it up.
  - **CLI.** `scf user delete <e-mail>` (account, sessions and credentials; refuses the only admin), `scf credential rotate-key` (re-encrypts everything under a new key) and `scf credential check` (stores, reads and removes a probe item).
  - **Code.** New `src/credentials/{keychain,store,redact,cli}.ts` and `src/server/api-credentials.ts`; `runProcess` takes an optional `redactor`; `withAuthLock` users call `removeCredentialsLocked`. `SCF_SECURITY_BIN` replaces `/usr/bin/security` and is for tests (the fake is `tests/fixtures/fake-security.mjs`).
  - **Not covered.** A UI page, using credentials in runs, other platforms, text written before a credential was saved (it is hidden in API answers but stays on disk), the task text in `run.json`, and other encodings such as base64 of `user:token`. Anyone who runs commands as your macOS user, flow steps included, can read the key.
  - **Please check once.** The real `/usr/bin/security` was not run when this was written: run `scf credential check` and `scf credential rotate-key` from a Terminal window.
